# Implementation plan — PRODUCT FIRST, repository second

**State:** PLANNED, not implemented. **Scope:** one portable WinSidebar executable for Windows 10/11 x64, with runtime UI support for English, Brazilian Portuguese, Spanish, Russian and Simplified Chinese, preserving existing working functions and settings. User-facing material follows the software; it never substitutes for it. Apply one locale per implementation/review stage, while making architecture and both en-US/pt-BR baselines available together for backwards compatibility.

## 0. Inventory and baseline contract

- Record commit SHAs and reproduce the existing `dotnet publish WinSidebar.csproj -c Release -r win-x64 --self-contained true -o publish` in Windows CI. Record the artifact hash. This is a baseline test, not a product acceptance test.
- Inventory **all application-owned strings** in `src/WinSidebar.cs` and `src/ShortcutConfig.cs`: labels, tooltips, accessible names/descriptions, tray/context menus, dynamic monitor labels and counts, shortcut defaults, editor combo labels, file-picker prompts/filters, warnings, startup/mutex and fatal error messages, failures and confirmation dialogs. Track each string in the traceability matrix. Preserve system-provided window titles, process names, P/Invoke identifiers, persisted `folder`/`website`/icon tokens, URLs, file paths and keyboard shortcut values.
- Freeze contract: collapsible sidebar, window enumeration and activation, per-monitor grouping, four configurable shortcuts, browser choice, icons, Shift+F1…F4, portable single EXE, no installer or separate .NET download, local settings, no automatic startup or telemetry. Document the deliberately excluded windows or change behavior explicitly after tests; do not silently change selection semantics during translation.

## 1. Architecture, persistence and migration

- Introduce a single lookup API (`Localization` or equivalent) and five UTF-8 locale dictionaries embedded as resources into the EXE; no runtime network lookup, external translation download, or language-specific fork. Use stable descriptive keys, e.g. `sidebar.folders`, `menu.exit`, `shortcut.validation.invalid_url`, `startup.already_running`, with parameterized messages. Resource choice is a proposed architecture, to be checked for actual .NET single-file behavior before it becomes a recorded decision; embedded `.resx`/ResourceManager is acceptable if integration tests show it is simpler and correct. Do not load untrusted external JSON as executable UI configuration.
- Validate all locale catalogs during build: same keys, no blank entries, correct placeholder names/types and brace escaping, valid UTF-8 and no unintended Portuguese in non-pt-BR application-owned strings. Format numbers and parameterized text using selected UI culture; never use translated keys as storage identifiers. Fallback order: exact supported locale -> supported language mapping -> `en-US`; log/report missing keys in dev builds and make locale-validation CI fail. No partially translated release.
- Locale codes: `en-US`, `pt-BR`, `es-ES`, `ru-RU`, `zh-CN`. The latter means Simplified Chinese, not Traditional Chinese. Windows `zh-Hans`/`zh-SG` can map to `zh-CN` only after verifying intended experience; `zh-Hant` must not be silently described as supported. English is GitHub default and unsupported-OS fallback, while supported Windows UI language may be auto-selected at first install.
- Persist manual language selection as a new non-destructive key in `%LOCALAPPDATA%\WinSidebar\settings.ini`. On legacy installations with an existing settings file but no language key, initially retain `pt-BR` so existing users are not surprised. If `settings.ini` does not exist, detect supported Windows UI language or fall back to `en-US`. A manual selection overrides detection and survives restart. Preserve every existing key, unknown forward-compatible keys if practical, and the browser/monitor/width settings. Define and test corrupted/read-only settings behavior without overwriting the original.
- Translate **visible default** shortcut names without mutating any user-edited names. Decide explicitly how pristine legacy defaults are detected: prefer provenance/flag on new installations and a conservative migration for exact known old defaults only when user intent can be distinguished; otherwise leave old names as user data. Never translate saved `Name`, `Target`, `IconFile`, `Type` or icon token by blind string replacement. Keep `shortcuts.xml` version 1 until a schema change is demonstrably needed. Protect backup, icon and browser preferences through every language switch.
- Refresh all visible controls, menus, tray labels, tooltips and accessibility text on a locale change, including dialogs opened subsequently; avoid losing focus/selection or triggering saves/shortcut launches. If immediate updating of an already-open modal cannot be made safe, postpone change until it closes with an explicit interaction rule. Disable locale choice only when absolutely required and explain why.

## 2. Incremental locale delivery (each is an independently tested change)

| Stage | Deliverable | Exit evidence |
| --- | --- | --- |
| L0 infrastructure | Central catalog, locale selection, persistence/migration, CI catalog checker | Complete key inventory; no behavior regression in Portuguese; new/legacy/invalid settings cases pass |
| L1 en-US + pt-BR | Complete English UI, Brazilian Portuguese regression, default-name treatment | Locale-switch/restart and keyboard/shortcuts/tray/editor/error paths work in both languages; no app-owned mixed-language text |
| L2 es-ES | Spanish catalog plus layout verification | Key parity, message formatting, 100/150/200% DPI UI capture and functional smoke |
| L3 ru-RU | Russian catalog plus Cyrillic/font layout | Same, including translated warnings and screen-reader names |
| L4 zh-CN | Simplified Chinese catalog plus glyph/font layout | Same, verified against Windows supported fonts and no unsupported traditional claim |
| L5 regression | Full five-locale functionality and stability | Test matrix complete on Windows 10/11 x64; zero unresolved release-blocking regressions |

Update the journal for each stage; never mark a locale delivered merely because a JSON/resx file exists.

## 3. Product hardening BEFORE marketing or release

- Window list: establish explicit inclusion/exclusion policy; check Calculator/Settings filtering for all target OS UI languages, minimize/restore, UWP/cloaked windows, task switching, selected-window persistence and other desktops as applicable. Avoid implying that *every* window is shown if intentionally excluded.
- Monitors and positioning: single monitor; two or more monitors; primary display changes; secondary unplug/replug; 100–200% DPI, font scaling, small work area, taskbar side, left/right sidebar, collapsed and expanded states. Avoid off-screen controls and unreadable window titles. Ensure hotkeys register/unregister without collisions or orphaned registrations; provide actionable error and mouse fallback.
- Shortcut lifecycle: add/edit/cancel/save, launch folder and HTTPS URL, default/custom browser validation, missing folder/browser/icon, malformed XML, denied writes, backup restore, file size constraints and icon orphan cleanup. No data loss when save fails.
- Accessibility: keyboard-only path to language selection, buttons/menus and shortcut editor; consistent focus, accessible names in chosen language, contrast, text truncation/tooltips and visible resize behavior. Standard Windows file dialogs may follow Windows language; document this boundary.
- Runtime readiness: clean first launch, repeated launch (single-instance), tray recovery, exit confirmation, restart and portable move, ordinary user privileges, no need to disable antivirus/IT policy. Establish manual update/rollback instructions; automatic updates and digital signing are not automatically required for this scoped portable tool, but lack of signature must remain prominent and accurately explained.

## 4. Packaging and reproducibility

- Expand project includes/resources and `.github/workflows/build.yml` triggers beyond two hard-coded sources. Run locale validation, automated tests, Windows build, structural ZIP audit, checksum generation and a smoke test where technically possible. Compile-only success != UI pass. Record package content expectations explicitly, including five localized plain-text quick starts such as `README.en-US.txt`, `README.pt-BR.txt`, `README.es-ES.txt`, `README.ru-RU.txt`, `README.zh-CN.txt`. Include one English default pointer only if it adds usability; do not ship an untranslated `LEIA-ME.txt` while advertising a complete English package. A resource catalog may be embedded in the EXE, keeping the portable behavior.
- Verify no personal paths, usernames, credentials or sample client data in source/resources, documentation, images, archive or CI logs. Keep the MIT license and unsigned executable notice. Produce a **new** release/version/tag and matching SHA256SUMS; do not overwrite v1.0.0 assets. If a signed binary is unavailable, do not claim one.

## 5. Repository internationalization ONLY AFTER product gates

- Canonical root `README.md` in English, plus `docs/i18n/README.pt-BR.md`, `.es-ES.md`, `.ru-RU.md`, `.zh-CN.md`; accurate navigation with no links to absent files. Each has a complete verified feature set, setup/remove/update instructions, privacy, constraints and security notice. English tutorial and Portuguese/Spanish/Russian/Chinese tutorials must match the actual UI language and **actual archive filenames**, rather than a fictitious filename or old `LEIA-ME.txt`.
- Translate both example illustrations (hero and square promo) per locale as editable SVG and rendered PNG with correct typography, natural line breaks and clear 'concept artwork, not a screenshot' disclosure in the illustration itself and in alt text. Preserve the intentional Windows 98 look. Test image size/overflow and link targets. If showing an actual screenshot, capture the tested software and label it accurately; never substitute a conceptual mockup.
- Translate end-user release notes, download instructions and any customer-facing quick starts; do not translate license terms, technical identifiers or external product names as if they were UI strings. Use English as repository landing/fallback, while application auto-detection may choose a supported language.

## 6. Promotion to final product

Release is blocked until every P0 gate in `VERIFICATION.md` has a reproducible PASS, every P1 has either PASS or an explicit documented scope decision, and product evaluation is updated using observations rather than presumed quality. Produce a clean release PR/branch **from approved main** and selectively bring in only shipping files; do not merge `develop` wholesale. Remove the premature `docs/i18n/LOCALIZATION-PLAN.md` from final `main`; exclude `development/**`, scratch documents, journal, unreleased draft references and obsolete legacy quick start. Verify final Git tree, ZIP manifest, runtime language menu, all five localizations, SHA256, release page and actual download again after publication. Restore/rollback using the previous release if any blocking check fails.

**Explicit non-goals without new user approval:** telemetry, accounts/cloud sync, paid subscriptions, auto-update service, bundled browser, support for Windows outside 10/11 x64, installer, or redesign replacing the Windows 98-inspired appearance. Do not inflate scope to declare the scoped utility 'complete'; measure completeness against the promised experience and documented constraints.
